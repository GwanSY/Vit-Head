# BumbleBee ViT

目前只实现全 Softmax 的 ViT-base 基线。没有改动原生推理协议，也没有加入异构头。
`model.py` 绑定 Transformers 缓存的 GELU 函数，保证实际编译出论文使用的 12 次 intrinsic GELU。

在本目录运行：

```sh
python run.py baseline
python run.py baseline --backend gpu
```

配置集中在 `config.json`。CPU 默认每方 25 线程；GPU 每方独占一张 A100，默认物理卡 0、1。
两方分别运行于隔离容器，网络每方向 1 Gbps、延时 0.25 ms；仅运行 ViT。
沿用本机 `openbumblebee` 容器里的 Python 依赖及 `openbumblebee-audit-deps` 镜像。
`build/` 保存运行库快照及 SHA256，不依赖临时目录中的原生库；原生库未重新编译，源文件哈希不代表构建版本证明。

每批只生成一个 `out/NN/`，拒绝覆盖旧目录。终端只显示关键状态；详细日志在 `log/`。
`run.json` 记录环境和哈希，`results.csv` 记录测量，`ops.csv` 对照论文算子，`logits.npz` 保存数值。
第一遍耗时超出门槛就省略其余重复；相近时再运行三遍。
门槛为论文时间 ±25%、总通信 ±10%，这是工程判断，论文没有规定此容差。

本轮结果在 `out/06/`：`results.csv` 和 `ops.csv` 包含已完成的 CPU 测量；GPU 只保存未完成试跑。
早期日志完整归档在 `log/old.zip`。CPU 为 401–410 秒、总通信约 11.17 GiB，尚未对齐论文 239.4 秒。
单图数值检查通过不代表 ImageNet 准确率已经验证。异构头、打包和分配协议均未开始。

`threads.csv` 是 197×768 乘 768×768 的秘密矩阵乘法诊断，不是完整 ViT。
每组一次冷启动、两次热运行；热运行中位数 CPU/25 线程为 1.06 秒，GPU/8、25、64 线程分别为 29.35、30.70、31.55 秒。
GPU 单方每次有 59,160 次上传、21,648 次下载；这些设备搬运字节不计为两方网络通信。
当前源码已有矩阵输入驻留缓存和打包树驻留路径，缓存 GPU 库的接口标记、计数字段与其不同；先核实构建身份，再评估新增优化。

后续研究按实测成本与精度可行性 → 异构执行开销定位 → GPU 分组打包 → 精度约束下联合选择头类型和批次 → 端到端消融展开。
区分秘密分享/密文转换和 CPU/GPU 搬运；BumbleBee 上异构头是否增加转换次数需要实测。
CPU/GPU × 全 Softmax/异构头四组对照使用同一个固定头方案，分别验证头替换和执行优化的收益。
